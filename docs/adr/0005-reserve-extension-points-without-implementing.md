# ADR-0005：收费、封控、监管留位不实现；多租户只加列

- 状态：已采纳
- 日期：2026-10-14
- 来源：用户第二轮补充意见第 3 点

## 背景

用户要求「框架搭建完善，预留后续添加功能空间，如收费、封控、监管」，
而蓝图明确「第一版不做收费和多租户」。两者需调和。

## 决策

**留位不实现**，但蓝图第 8 节已要求的照做：

| 领域 | 第一版 | 预留方式 |
|------|--------|---------|
| 计费 | 只记用量与费用，不结算 | `unit_price_snapshot`、`cost_center`、`/admin/billing` 占位路由、`billing` 中间件空实现 |
| 封控 | 预算上限、登录限流、模型白名单（蓝图已要求） | `quota` 中间件、`users.is_suspended`、限流器接口 |
| 内容审核 | 无 | `content_policy` 中间件（入站/出站钩子）、`policy_events` 表 |
| 监管 | 审计日志全量落地（蓝图已要求） | 留存期配置、`/admin/audit/export`、出境开关 |
| 多租户 | 不做隔离 | 关键表加**可空** `tenant_id`，只加列不加逻辑 |

横切逻辑走**中间件链**（请求ID → 认证 → 授权 → 配额/预算 → 内容策略 → 审计 → 计量）。
策略点与实现分离，第一版挂 `Noop*` 实现。

## 理由

加一个可空列、一个空实现几乎零成本；将来补功能时不用改所有查询与业务函数。
但第一版不引入用不上的复杂度与运维负担。

## 后果

- 需要克制：留位不等于提前实现，避免过度设计。
- `tenant_id` 列在单租户下恒为 NULL，查询层需统一经 `scope` 过滤以便将来启用。
