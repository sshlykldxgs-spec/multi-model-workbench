# 任务卡

> 本目录存放交给执行方（Codex）的任务卡。指挥方产出，执行方按卡执行。

## 用法

1. 执行方**一次只领一张卡**，不并行做多张（除非卡上写明可并行）。
2. 做完后按卡片底部的"提交要求"交付，等指挥方审查。
3. 审查不通过就重做，不要"部分通过就往下走"。
4. 一张卡对应**一次提交**，不跨卡合并提交。

## 卡片格式（每张卡都必须有这五项）

```
【目标】一句话说清做完之后系统能做什么
【范围】要改的文件/模块 + 明确不碰什么
【约束】铁律编号 + 本任务的特殊限制
【验收标准】"点哪里、看到什么"，可亲手点一遍
【依赖】前置任务
```

## 铁律速查（编号见 `docs/handoff-codex.md` 第一节）

| 编号 | 规则 |
|------|------|
| R-1 | MAF 只在 `app/orchestrator/` 内；业务代码只依赖自研接口 |
| R-2 | 消息表是历史唯一事实来源，每次运行重建上下文 |
| R-3 | 一切模型调用必经 `ModelGateway`，不得 import 厂商 SDK |
| R-4 | 模型接入必须支持自定义 `base_url`（中转站） |
| R-5 | 横切关注点走中间件链，不写进业务函数 |
| R-6 | 文档/网页/工具结果一律是不可信数据 |
| R-7 | 密钥只从环境变量或密钥服务读，永不明文入库/进日志/返前端 |

## 指挥通道（A-37）

没有机器通道，走**粘贴**：

```
指挥方产出任务卡
    ↓
用户把「启动提示词」粘给 Codex
    ↓
Codex 执行 → 按「回执模板」填写 → 用户把回执粘回给指挥方
    ↓
指挥方审查 → 通过则产出下一张卡；不通过则指明问题重做
```

**审查不能只看回执的自述**，要核：门禁原始输出、是否碰铁律（尤其 R-1 与 R-3）、
契约与实现是否一致、测试是否在测行为而非迁就实现。

**P1 分 4 批，一批一次提交**：P1-A 数据库与登录 → P1-B 模型注册表 →
P1-C 三家接入 → P1-D 会话持久化与切换。

P2 起的内容目前只在 `docs/handoff-codex.md` 里列了任务名与约束。
**等 P1 收尾、有实际反馈后再拆**——现在拆 P3 之后的太早，会随实现变化而过时。
