# 第一部分：开发期工具（写这个项目时用）

目标：让"前后端各一个 AI 会话"这种开发方式**不跑偏、不退化、不重复劳动**。
你点名的四件事——上下文压缩、逻辑优化、前端制作——全部覆盖。

## A1. 上下文与记忆管理（你点名的第 1 项）

前后面临的真问题：长会话上下文膨胀、会话切换后丢信息、两个会话各说各话。

| 工具 / 做法 | 解决什么 | 怎么用 |
|------------|---------|--------|
| **`CLAUDE.md` / `AGENTS.md` 文件** | 会话间的事实传递 | 替代"各自聊天记忆"。本项目已建两份 `AGENTS.md`，这是**最有效的一条**，优先于任何插件 |
| **`docs/PROGRESS.md`** | 会话交接 | 每个会话结束前更新，新会话开工前先读 |
| **`/compact`（Claude Code 内置）** | 上下文压缩 | 长会话中途压缩，保留摘要继续 `[常识]` |
| **持久记忆目录** | 跨会话记住偏好与结论 | 一条事实一个文件 + 索引。已启用 |
| **记忆整合 skill** | 合并重复、清理过期条目 | 定期跑一次，防止记忆腐化 `[已核]` |
| **`/clear` + 重开新会话** | 防止上下文污染 | 换阶段就换会话，别硬撑 |
| **handoff 类 skill** | 生成结构化交接摘要 | Codex 生态有 `handoff` skill；Claude 侧可用提示词实现 `[待核]` |

**给你的具体建议**：不要依赖插件做记忆。**靠 `AGENTS.md` + `PROGRESS.md` + `decisions.md`
这三个文件**，它们可读、可审、可进 Git。插件是补强，不是地基。

## A2. 代码审查与质量控制（你点名的第 2 项"逻辑优化"）

| 工具 | 解决什么 | 备注 |
|------|---------|------|
| **`/code-review`（Claude Code 内置）** | 审 diff 找正确性 bug | 支持按 effort 级别跑，产出带文件行号的发现 `[已核]` |
| **`/security-review`（内置）** | 安全审查 | 对本项目尤其重要（提示词注入、凭据） `[已核]` |
| **`/simplify`（内置）** | 复用、简化、效率、抽象层级 | "逻辑优化"直接对应这个 `[已核]` |
| **交叉模型审查** | 防自我确认 | **用另一个模型审 Claude 的代码**。这是蓝图第 10 节的建议，也是防"自己给自己打高分"的关键 |
| **OpenCodeReview** | 产品要接的评审工具 | 同一套东西先在开发期用一遍，等于提前替 P4 做验证 |
| **`ruff` + `pyright`** | 静态检查 | 后端门禁，见 `backend/AGENTS.md` |
| **`eslint` + `tsc --noEmit`** | 前端门禁 | 见 `frontend/AGENTS.md` |

**关键原则**（来自蓝图）：**审查和写代码的不要是同一个会话**。所以流程是
「后端会话写代码 → 另一个会话/另一个模型审」。这一点比装什么插件都重要。

## A8. 若只能装 5 个

## A9. Codex 生态（你单独问的部分）

`[已核]` 程度有限，且部分来源是内容营销，**数值与排名一律不可信**。可靠的说法：

- OpenAI 的 skill 仓库 `openai/skills` 已标记**弃用**，转向新的 Plugins 仓库 `[已核]`。
- 技能仓库按 `.system`（随 Codex 自动装）、`.curated`、`.experimental` 三档组织；
  许可**逐技能**看各自目录内的 `LICENSE.txt`，仓库整体未声明统一许可 `[已核]`。
- 安装方式为 `$skill-installer <名称>` 或按目录 URL 安装，装完需重启 Codex `[已核]`。
- 社区生态里被反复提到的有 Superpowers、Context7、Firecrawl、Playwright/Chrome DevTools MCP、
  GitHub MCP 等 `[已核，但来源质量参差]`。

**结论**：Codex 生态可以挑着用（尤其 Context7 与 Playwright 两边都有），
但**不要照搬任何"必装清单"**。本项目的实际瓶颈不在工具数量，在

# 第二部分：产品内置技能系统（工作台要实现的东西）

对应 `design.md` 第 6A 节。这一部分是**产品需求**，不是给你装工具。

## B1. 目标

工作台里的角色（Planner / Worker / Reviewer / 自定义）可以挂载**技能**：
一段可复用的指令 + 可选附带资源。技能要能**存数据库、可分享、可版本管理**。

## B2. 需要实现的组件

| 组件 | 职责 | 阶段 |
|------|------|------|
| `Skill` 数据结构 | 名称、描述、触发条件、指令正文、附带资源、可见范围 | P5 |
| `SkillRegistry` 抽象 | 技能的增删改查、按角色解析 | P5 |
| `DbSkillRegistry` | 第一版实现，存数据库，随 `config_versions` 做版本管理 | P5 |
| `MafSkillAdapter` | 适配 MAF Skills 的**可选**实现，不进核心路径 | P5 之后，视核实结果 |
| 技能分享 | 复用配置区已有的 `shares` 机制，默认只读、可"复制后修改" | P5 |
| 技能版本与回滚 | 与角色/画布同一套版本机制 | P5 |
| 发布前校验 | 技能引用的资源是否存在、指令长度是否超限 | P5 |

## B3. 硬约束

- 技能**不授予权限**。技能不能扩大角色可用的工具集与知识库范围——
  那些仍由角色配置与**运行者权限**决定（蓝图规则，`design.md` 7.4）。
- 技能正文属**受信配置**（成员自己写的），但技能**附带的外部资源**
  （脚本、下载的文档）仍按**不可信数据**处理（R-6）。
- 技能不得包含密钥。需要凭据的能力必须走工具与凭据机制。
- 技能的分享与可见范围**服从现有权限模型**，不另起一套。

## B4. 为什么自研而不用 MAF Skills

MAF Skills 仍是**预览功能**（A-21、ADR-0004）。预览功能难以稳定支撑
「可分享 + 可版本管理 + 与权限模型一致」三项要求。故自研接口，MAF 作可选实现。
`[待核]` MAF Skills 的确切机制尚未核实，核实后再定是否值得做 `MafSkillAdapter`。
