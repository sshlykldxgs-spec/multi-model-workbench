  5.结果、事件和⽤量写⼊数据库。

5. 核⼼模块设计

核⼼思路：业务代码只依赖⾃⼰定义的接⼝，MAF 被限制在“编排层”内，这样框架升级或预览功
能变动时，影响范围可控。

5.1 Planner–Worker–Reviewer 核⼼分⼯（根据你的补充）

  •  Planner：把⽤户任务拆成步骤清单，每步写明负责的 Worker 类型和验收标准，输出结构
     化的计划。

  •  Worker：按步骤执 ⾏，可调⽤⼯具、MCP     和知识库；互不依赖的步骤可并       ⾏执⾏。

  •  Reviewer：对照验收标准检查每   ⼀步和最终结果，给出“通过”或“退回并说明原因”；退回
     后回到 Worker，默认最多重做 2 轮。

  •  汇总：通过后输出最终答案，并附上步骤记录。

实现⽅式：⽤ MAF 的图⼯作流把三个⻆⾊连成“规划 → 执⾏ → 评审 → 退回或通过”，⽽不是把所
有事塞进⼀个⼤提示词。三个⻆⾊可以各选模型，例如 Planner 和 Reviewer ⽤较强的模型，
Worker ⽤性价⽐⾼的模型，并让     Reviewer 与 Worker 使⽤不同的模型或提示词，避免“⾃⼰给⾃⼰
打⾼分”。可配置项：最⼤轮数、预算上限、规划后是否需要⼈⼯确认。另外提供四种通⽤模板
（顺序、并发、交接、群聊），MAF 1.0 已稳定⽀持这些编排模式。

关于 OpenCodeReview（按你确认的阿⾥ alibaba/open-code-review）

  •  它是命令⾏⼯具，⽤ npm 安装，依赖 Git 2.41 或更⾼版本，兼容 OpenAI 和 Anthropic ⻛格
     的 API，Apache 2.0 开源。

  •  所以接⼊它需要：⼀个带 Git 的代码⼯作区（沙箱）、Node 环境，和模型 API 密钥。

  •  它⾃⼰也会调⽤模型，这部分⽤量和数据外发要纳⼊预算与审计。

  •  它的输出格式我没有核对细节，P4 开始前要先做⼀次⼩验证：确认输出能否稳定解析、在

     沙箱⾥能否跑通。

5.2 模型接⼊层

========== PAGE 8 ==========
  • 模型注册表：⼚商、模型名、能⼒标记（流式、⼯具调⽤、图⽚、上下⽂⻓度）、单价、
    启⽤状态，由管理员配置，不写死在代码⾥。

  • 通过 MAF ⾃带的连接器接⼊三家模型，业务代码只依赖⾃定义的 ModelGateway 接⼝。

  • 统⼀超时、重试、限流错误处理；提供 mock 模型，供前端联调和⾃动测试使⽤。

5.3 会话与记忆

  • ⾃⼰的消息表是历史的唯⼀事实来源，每次运⾏时再重建给 MAF 的上下⽂。原因：中途
    切换模型需要中性格式的历史；我没有验证 MAF 序列化的会话能否跨⼚商复⽤，所以不
    依赖它。

  • ⻓对话的裁剪或摘要策略放在这⼀层；跨会话的⻓期记忆第⼀版不做，只预留接⼝。

5.4 ⼯具与 MCP

  • ⼯具注册表包括内置函数⼯具和 MCP 服务器；MCP 服务器配置包含地址、认证⽅式、允
    许调⽤的⼯具⽩名单。

  • 每个⼯具标⻛险级别（只读、写⼊、破坏性）；写⼊和破坏性操作必须经⼈⼯确认，⽤
    MAF 的 human-in-the-loop 请求机制实现，⼯作流运⾏会暂停等待确认。

  • 第⼀版只⽤“由我们进程发起调⽤”的 MCP，不⽤⼚商托管的 MCP。原因：托管 MCP 的调
    ⽤由模型⼚商的服务发出，我们的⽩名单、审批和审计⽇志看不到。

  • 调⽤设超时和结果⼤⼩上限。

5.5 知识库

  1.上传后校验类型与⼤⼩，写⼊任务表。

  2.worker 解析（txt、md、docx、⽂字型 PDF）、分块、向量化，写⼊ pgvector。

  3.⽂件状态：排队、处理中、可⽤、失败，前端可⻅。

  4.检索以“搜索知识库”⼯具的形式提供给 agent，由 agent 决定何时检索；回答附引⽤（⽂件
    名、⻚码或段落）。

  5.删除⽂件时同步删除分块；分块记录嵌⼊模型名，以便以后换模型重建索引。

扫描件 PDF 的 OCR 和复杂表格解析第⼀版不做。

5.6 运⾏与状态

========== PAGE 9 ==========
  • ⼀次“运⾏”指⼀次对话回合或⼀次⼯作流执⾏，状态：排队、运⾏中、等待确认、成功、
    失败、已取消。

  • MAF ⼯作流⽀持检查点和暂停恢复，但我从⽂档⾥只看到内存存储和⽂件存储的示例，没
    有查到官⽅的 Postgres 实现，所以 P4 需要⾃⼰实现⼀个数据库⽀持的检查点存储。

  • ⽀持取消、超时、预算上限中⽌；刷新⻚⾯后可⽤运⾏编号重新连上事件流。

5A. 个性化配置区（与⼯作区分离）

产品分成两个区域：⼯作区只负责“⽤”，配置区负责“设计和调整”。两区共⽤后端，但⼊⼝、界
⾯和数据状态分开，改配置不会影响正在运⾏或已完成的任务。

区域                 做什么                谁⽤

⼯作区                对话、上传⽂件、选择已发布      全体成员
                   的分⼯、发起运⾏、查看结
                   果、审批

配置区                创建⻆⾊、画布编排分⼯、试      全体成员，各管各的，可分享
                   运⾏、版本管理、导⼊导出、
                   分享

配置区的能⼒

  1.⻆⾊库：创建、复制、分类，也可以从官⽅模板开始。⼀个⻆⾊包括：名称、职责说明、
    指令、执⾏者（单模型、模型组、外部⼯具、外部服务、⼈⼯）、模型、可⽤⼯具和知识
    库、输出格式、预算和轮数上限。

  2.分⼯画布：拖拽⻆⾊节点并连线，⽀持顺序、并⾏、条件分⽀、评审退回循环和⼈⼯确认
    点；节点上可以随时替换执⾏者。MAF 1.0 的图⼯作流本身⽀持条件分⽀、并⾏扩散和汇
    聚，画布就是它的可视化编辑器。

  3.试运⾏：⽤示例输⼊在隔离环境⾥跑，逐步查看输⼊输出、耗时和费⽤；不进⼊正式会
    话，费⽤计⼊运⾏者的预算。

  4.版本与发布：改动先保存为草稿，试运⾏满意再“发布”⽣成新版本。⼯作区只使⽤已发布
    的版本，可回滚到任⼀历史版本；每次运⾏都记录所⽤的配置版本，历史运⾏可复现。

  5.导⼊导出：配置可导出为⽂件⽤于备份和分享。MAF 1.0 ⽀持⽤ YAML 声明 agent 和⼯作
    流，导出格式尽量贴近它，画布布局等信息另存，具体字段 P5 开始前再核对。

========== PAGE 10 ==========
  6.分享：默认私有，可分享给指定成员或全团队，被分享的配置默认只读，可“复制后修
    改”；管理员可把配置设为官⽅模板。

  7.发布前校验：⾃动检查是否有孤⽴节点、循环是否设了最⼤轮数、引⽤的模型、⼯具和知
    识库是否可⽤、是否设了预算上限。

规则：配置只决定“⽤什么、怎么分⼯”，不授予额外权限。⼯具审批、预算和知识库可⻅范围永
远按“运⾏者”的权限计算，所以别⼈分享的配置不能让你越权。

前端⼯作量提醒：拖拽画布是整个项⽬前端最重的⼀块，所以它单独成⼀个阶段（P5），建议基
于成熟的流程图组件库实现，不要让 AI 从零⼿写画布。Planner–Worker–Reviewer 核⼼模板在这⾥
就是⼀份官⽅模板，可以复制后随意改。

8. 安全与权限

最⼤的⻛险不在登录，⽽在“模型被不可信内容诱导去调⽤⼯具”和“⽂档数据流向第三⽅”。

  •  账号：管理员邀请制，密码⽤ argon2 哈希，会话 Cookie 设为 HrpOnly 和 SameSite，登录
     限流；⻆⾊只有管理员和成员。

  •  密钥：模型⼚商密钥和 MCP 凭据只存在服务端，前端永远接触不到；⽇志必须脱敏；定
     期轮换。

  •  ⼯具调⽤：⽩名单加⻛险分级，写⼊和破坏性操作默认需要⼈⼯确认；来⾃⽂档、⽹⻚、
     ⼯具结果的内容⼀律当作不可信数据，其中的“指令”不能提升权限；⼯具只拿最⼩权限的
     凭据。

  •  代码与外部⼯具任务：在沙箱容器⾥运⾏，限制⽹络、资源和运⾏时间，⼯作⽬录按任务
     隔离。

  •  ⽂件：类型⽩名单和⼤⼩上限，解析放在 worker 进程，存储路径不由⽤户决定，下载要

     鉴权。

  •  知识库隔离：检索时按可⻅范围过滤，避免⼀个⼈搜到别⼈的私有⽂件。

  •  数据外发：上传的内容和对话会发送给所选模型⼚商，界⾯上要标明；管理员可以限制某
     个知识库只能⽤指定模型。

========== PAGE 15 ==========
  • 审计：登录、⼯具审批、⽂件上传和删除、配置变更都写⼊审计⽇志。

9. 部署与运维

第⼀版部署在单台服务器上，⽤ Docker Compose ⼀条命令起停，重点放在“可观测”和“花钱可控”
上。

  • 环境：开发环境⽤ mock 模型加本地 Postgres；CI 跑测试和契约检查；⽣产环境由反向代
    理（Caddy）、API、worker、Postgres（含 pgvector）、前端静态⽂件和代码沙箱容器组
    成。

  • 配置：⽤环境变量管理，提供 .env.example；密钥不进仓库、不进数据库明⽂。MAF 不会
    ⾃动读取 .env，程序启动时要显式加载。

  • 可观测性：开启 MAF ⾃带的 OpenTelemetry 追踪，⼀次运⾏⾥的模型调⽤、⼯具调⽤、⼯

    作流步骤都能串成⼀条链；结构化⽇志带 run_id 和 user_id，并脱敏；指标包括请求量、
    延迟、错误率、token 和费⽤。

  • 成本控制：每⼈每⽇、每⽉预算，每次运⾏的预算上限；⼯作流最⼤轮数（Planner–
    Worker–Reviewer 的退回循环和群聊最容易失控）；模型⽩名单；超过预算 80% 时提醒，
    超过 100% ⾃动中⽌运⾏。

  • 备份：Postgres 每⽇备份，上传⽂件⽬录同步备份，定期做⼀次恢复演练。

  • 升级：依赖全部锁定版本；MAF 升级单独提交，并跑完回归⽤例再合并。

  • 沙箱：代码任务在独⽴容器⾥运⾏，限制 CPU、内存和运⾏时间，默认不开放外⽹，只允
    许访问必要的地址。

  • ⽹络：服务器必须能稳定访问所选模型⼚商的 API，这⼀点在第 12 节单独说明。
